## 5.1 캐시, 어디에나 존재하는 것

메모리에 읽고 쓸 일도 넘쳐나는데 CPU 내부의 레지스터는 좁아터졌다.

결국 메모리를 쓸수 밖에 없는데 메모리는 CPU 속도와는 비교도 안될만큼 느려터졌다.

```
메모리가 느린이유

DRAM의 구조적 한계: DRAM은 정보를 **축전기(Capacitor)**에 전하로 저장합니다. 이 축전기에 전기를 충전하거나 방전하는 데 걸리는 물리적/화학적 시간을 줄이는 데 한계가 있습니다.

재충전(Refresh) 동작: DRAM의 전하는 시간이 지나면 자연적으로 방전되므로, 데이터를 유지하기 위해 주기적으로 재충전(Refresh) 동작이 필요합니다. 이 재충전이 일어나는 동안에는 메모리 접근이 제한되어 속도에 제약이 생깁니다.

CPU와 메모리의 거리: CPU는 메인보드의 소켓에 장착되고, RAM 모듈은 슬롯에 장착되어 **인쇄 회로 기판(PCB) 상의 긴 배선(인터커넥트)**을 통해 연결됩니다.

신호 전송의 제약: 클럭 신호가 이 긴 거리를 고속으로 정확하게 전송되려면, 신호 무결성을 유지하고 전송 지연을 최소화해야 합니다. CPU 내부의 짧은 배선보다 더 긴 외부 배선을 통해 데이터를 주고받는 것은 신호 전송 속도에 또 다른 제약을 가합니다. RAM의 클럭은 이 인터커넥트의 타이밍을 최적화하도록 설계됩니다.
```

지금의 CPU는 CPU와 메모리 사이에 캐시를 둔다.

캐시에는 최근에 메모리에서 얻은 데이터가 저장되며, CPU는 메모리에 접근하기 전에 먼저 캐시를 찾아본다.

> 그럼 캐시 적중률이 낮을수록 속도가 느려지겠네?

캐시 갱신의 문제 = 캐시의 데이터와 메모리의 데이터가 불일치 하는 문제.

해결책 1. 캐시 갱신시 메모리도 동기적으로 갱신 ~~듣기만 해도 느릴거 같다~~

해결책 2. 캐시 갱신시 메모리 갱신은 비동기적으로 한다. ~~근데 갱신 속도가 변경속도를 못따라 잡으면 어떻게 되는거지~~

```
캐시 불일치 (Cache Coherence Problem): 특히 멀티코어 시스템에서 다른 CPU 코어가 해당 메모리 주소의 데이터를 읽으려고 할 때, **메모리(주 메모리)**에서 가져온 데이터가 이미 갱신된 캐시의 데이터와 달라져 잘못된 값을 사용하게 됩니다.

CPU 스톨 (CPU Stall): 메모리 갱신 속도를 따라잡지 못하는 경우, CPU는 갱신이 완료될 때까지 작업을 **일시 중지(Stall)**하고 기다려야 합니다. 이는 CPU의 빠른 연산 능력을 제대로 활용하지 못하고 시스템 성능을 저하시킵니다.

from Gemini
```

```
해결 메커니즘: Write Buffer와 캐시 일관성 프로토콜

비동기적인 갱신 환경에서 속도 불일치로 인한 문제를 해결하기 위해 다음과 같은 하드웨어 및 소프트웨어적 메커니즘이 사용됩니다.

A. Write Buffer (쓰기 버퍼)
비동기 갱신 방식(주로 Write-Back 캐시 정책에서 사용)에서 CPU가 캐시의 데이터를 갱신했을 때, 그 변경 사항을 즉시 메모리에 반영하지 않고 Write Buffer라는 임시 저장 공간에 빠르게 기록합니다.

작동: CPU는 Write Buffer에 데이터를 기록한 후 즉시 다음 작업을 수행할 수 있습니다(Vcache_change유지). 메모리 컨트롤러는 CPU가 바쁘지 않을 때나 버퍼가 가득 찼을 때 비동기적으로 Write Buffer의 내용을 메인 메모리에 반영합니다(Vmemory_update진행).

문제점: Write Buffer가 가득 찼는데 CPU가 또 쓰기 요청을 하면, CPU는 버퍼가 비워질 때까지 Stall해야 합니다.

from Gemini
```

다중코어를 쓰면 각 코어마다 캐시의 값이 다를수 있기 때문에 캐시끼리도 동기화 시켜햐 한다 ~~산너머 산이네~~

> 그냥 공통캐시를 쓰면 너무 비싸지나?

최신 CPU에는 MESI Protocol 같은 규칙으로 동기화를 시킨다.

```
B. 캐시 일관성 프로토콜 (Cache Coherence Protocols)
멀티코어 시스템에서 캐시와 메모리의 데이터 일관성을 유지하기 위해 사용됩니다. 대표적으로 스누핑(Snooping) 기반의 MESI 프로토콜이 있습니다.

작동: 한 코어의 캐시에서 데이터를 갱신(Write)하면, 다른 코어들은 이 갱신 사실을 감지하고(Snoop) 자신들의 캐시에 있는 해당 데이터 블록을 무효(Invalidate) 처리하거나(Write Invalidate) 최신 값으로 업데이트(Write Update)합니다.

효과: 이로써 다른 코어가 갱신되지 않은 메모리의 오래된 데이터가 아닌, 가장 최신의 캐시 데이터를 사용하도록 강제하여 데이터 불일치 문제를 방지합니다.

C. Write Through (쓰루) 정책 (간접적 해결)
이는 엄밀히 말해 비동기 방식의 단점을 해결하는 방법이라기보다는 다른 갱신 정책입니다.

작동: 캐시에 데이터를 쓸 때 동시에 메인 메모리에도 데이터를 씁니다.

효과: 캐시와 메모리의 데이터가 항상 일치하므로 불일치 문제는 발생하지 않지만, 가장 느린 메인 메모리 속도에 맞춰야 하므로 CPU의 성능 향상 효과가 감소합니다.

from Gemini
```

메모리보다도 느려터진 저장장치를 위해 메모리는 저장장치의 캐시 역할도 한다.

그리고 메모리 용량이 좁아 터지기 시작하면 저장장치가 가상 메모리의 역할도 한다.

> 그래서 SSD 쓰는 컴퓨터가 빠른것이다.

현대 CPU가 메모리를 읽는 법

L1 캐시를 찾는다 -> L2 캐시를 찾는다 -> L3 캐시를 찾는다 -> 메모리를 찾는다 -> 저장장치를 찾는다 -> 저장장치의 내용을 메모리로 로드한다. -> 메모리의 내용을 캐시에 쌓는다 ~~CPU야 힘내 ㅜㅜ~~

분산 파일 시스템에서는 로컬 드라이브나 메모리가 네트워크에 연결되어서 캐시 역할을 한다.

## 5.2 어떻게 캐시 친화적인 프로그램을 작성할까

CPU를 힘들게 하지 않으려면 느린 쪽의 hit rate를 줄이면 된다.

프로그램 지역성의 원칙 : 프로그램이 매우 규칙적으로 메모리에 접근한다.

캐시 친화적인 프로그래밍 원칙

1. 메모리 풀 사용: 큰 메모리를 미리 할당하여 메모리 연속성을 보장한다.
2. struct 구조체 재배치 : 구조체의 속성 선언시에 각 속성사이에 너무 큰 데이터 공간을 할애하지 않는다.
3. 핫 데이터와 콜드 데이터 분리 : 예를 들어 링크드 리스트의 경우 실제 데이터 버퍼보다 다음 노드의 포인터가 더 많은 hit rate를 가질수 있으므로, 링크드 리스트의 구조체 안에 데이터 버퍼는 외부로 빼고 버퍼의 포인터를 갖게 한다.
4. 캐시 사이즈에 맞춰 데이터 크기를 선언한다 ~~근데 이건 너무 극한인듯~~
